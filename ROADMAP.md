## 1. Исправления (баги и несоответствия)

### 1.1 Поиск
- [ ] **Починить мёртвый GIN-индекс.** Индекс построен по
      `to_tsvector('simple', content_text)`, а запрос `SearchPages` фильтрует по
      `title || ' ' || content_text` — выражения не совпадают, индекс не
      используется (seq scan). Решение: генерируемая tsvector-колонка
      (`GENERATED ALWAYS AS ... STORED`) + GIN по ней, запрос — по колонке.
- [ ] **Русская морфология.** Конфигурация `'simple'` не стеммит: «настройка»
      не находит «настройки». Перейти на `russian` (или `russian || simple`
      для смешанных текстов), обновить и колонку, и `plainto_tsquery`.
- [ ] (опц.) Опечатки/частичные совпадения: `pg_trgm` + similarity как fallback,
      когда FTS ничего не нашёл.

### 1.2 Дерево страниц
- [ ] **Защита от циклов в `move`.** `PATCH /pages/:id/move` и MCP `move_page`
      позволяют перенести страницу в её собственного потомка → поддерево
      становится недостижимым. Проверять предка рекурсивным CTE, отвечать 400.
- [ ] **Переиндексация позиций соседей.** `MovePage` пишет `position` без сдвига
      соседей — значения расходятся. Пересчитывать позиции в старом и новом
      родителе в одной транзакции.

### 1.3 Файлы
- [ ] **GC осиротевших файлов.** Удаление картинки из редактора не удаляет
      запись в `files` — растёт навсегда. Варианты: периодическая задача,
      сверяющая `files.id` с упоминаниями в `pages.content`, или подсчёт ссылок
      при сохранении страницы.

## 8. Авторизация: социальные провайдеры

Сейчас приложение только валидирует JWT от внешнего IAM-прокси. Цель — вход
через популярных провайдеров (Google, Apple, Yandex, VK и др.) без обязательного
внешнего IAM.

- [ ] **Архитектурное решение** (сначала!): встроенный OAuth2/OIDC-клиент в
      приложении vs брокеринг через IAM (Keycloak умеет всех перечисленных
      провайдеров из коробки — тогда в коде ничего менять не надо, только
      документация по настройке). Если встроенный — пункты ниже.
- [ ] Встроенный OIDC/OAuth2-флоу: `/auth/login/:provider`, callback, выпуск
      собственной сессии (cookie или свой JWT), refresh, logout.
- [ ] Провайдеры: Google, Yandex, VK (OAuth2 без полноценного OIDC — свой
      маппинг профиля), Apple (Sign in with Apple: свой JWT-клиентский секрет,
      ротация ключей). Конфигурация провайдера = client_id/secret + redirect.
- [ ] Таблица `users` (subject провайдера → локальный пользователь: имя,
      email, аватар) — связка с разделом 3 «Авторство».
- [ ] Привязка нескольких провайдеров к одному пользователю (по email или
      явная привязка в профиле).
- [ ] Роли: читатель / редактор / администратор — хранение в БД, назначение
      через админку (раздел 9); маппинг групп из JWT оставить для IAM-режима.
- [ ] Экран входа: кнопки провайдеров (показывать только настроенных),
      режим `publicRead` сохраняется.

## 9. Страница администрирования

Все настройки, которые сейчас живут только в `appsettings.yaml`/env, должны
управляться администратором через UI без рестарта.

- [ ] **Хранение настроек в БД** (таблица `settings`, key/value или JSONB) с
      приоритетом: env > БД > yaml > дефолты; горячее применение без рестарта
      (перечитывание/подписка). Секреты (client_secret, hmac) — шифровать или
      помечать write-only (в UI не показывать значение).
- [ ] **Роль администратора** + гард `RequireAdmin` (зависимость: раздел 8,
      роли). Первый админ — назначение через env/CLI (bootstrap).
- [ ] API: `GET/PUT /api/admin/settings` (+ аудит изменений: кто, когда, что).
- [ ] UI-страница `/admin` (видна только админам), секции:
  - [ ] Брендинг: название, монограмма, тема по умолчанию (сейчас —
        `branding` в yaml).
  - [ ] Авторизация: вкл/выкл, режим (IAM JWT / встроенные провайдеры),
        JWKS/issuer/секрет, `publicRead`, `editorGroups`, настройка
        провайдеров из раздела 8.
  - [ ] Пользователи и роли: список, назначение читатель/редактор/админ.
  - [ ] Лимиты: `maxUploadBytes`, retention ревизий (связка с разделом 2).
  - [ ] Данные: перенести сюда экспорт/импорт БД (сейчас в меню оформления)
        и запуск GC файлов (раздел 1.3).
  - [ ] Импорт: запуск импорта из Confluence с прогрессом (раздел 7) —
        альтернатива CLI.
- [ ] Кнопка «проверить подключение» для JWKS/провайдеров (валидация настроек
      до сохранения).

## 10. Проекты (пространства) и их ролевая модель

Сейчас все страницы живут в одном общем дереве, а права глобальные
(читатель/редактор на всё приложение). Цель — изоляция по проектам в духе
спейсов Confluence: у каждого проекта своё дерево страниц и свои участники
с ролями.

- [ ] **Модель данных**: таблица `projects` (ключ, название, иконка,
      описание, видимость), `pages.project_id NOT NULL`; миграция существующих
      страниц в дефолтный проект.
- [ ] **Ролевая модель на проект**: таблица участников
      (`project_members`: user × project × роль). Роли: читатель / редактор /
      администратор проекта. Глобальный админ (раздел 8) видит и управляет
      всеми проектами.
- [ ] **Видимость проекта**: публичный (читают все, в т.ч. анонимно при
      `publicRead`) / внутренний (все вошедшие) / приватный (только участники).
- [ ] **Гарды на бэке**: все проверки прав (`RequireEditor` и т.п.) становятся
      проектными; доступ к странице выводится из её проекта. Дерево, поиск,
      файлы и ревизии фильтруются по доступным проектам.
- [ ] **UI**: переключатель/список проектов (сайдбар или главная), дерево и
      поиск в рамках текущего проекта (+ глобальный поиск по доступным),
      управление участниками — админом проекта (страница настроек проекта).
- [ ] **Затронутые подсистемы** — пройтись по всем:
  - [ ] поиск: фильтр по проекту + права (раздел 1.1);
  - [ ] MCP-инструменты: параметр проекта в `list_pages`/`create_page`/…,
        те же проектные права;
  - [ ] бэкап: экспорт/импорт всего или одного проекта (раздел 4);
  - [ ] импорт из Confluence: спейс → проект (раздел 7);
  - [ ] move: запрет переноса страниц между проектами либо явная операция
        с проверкой прав в обоих.
- [ ] Зависимости: таблица `users` и роли (раздел 8), назначение ролей через
      админку (раздел 9). Делать после них — иначе некому назначать права.

## Порядок работ (рекомендация)

1. **1.1 Поиск** — маленький diff, заметен каждому каждый день.
2. **3 Авторство** — дёшево сейчас, дорого потом (данные без авторов).
3. **2 Тесты** (конвертер + бэкап + CI-шаг) — страховка перед остальным.
4. **1.2 Дерево** и **1.3 Файлы**.
5. **5 Дистрибуция** — когда захотим отдавать другим командам.
6. **8 → 9 → 10**: провайдеры и роли → админка → проекты (проектам нужны
   пользователи, роли и управление ими).
7. Дальше — 4, 6, 7 по потребности.
