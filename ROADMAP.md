## 8. Авторизация: социальные провайдеры

Сейчас приложение только валидирует JWT от внешнего IAM-прокси. Цель — вход
через популярных провайдеров (Google, Apple, Yandex, VK и др.) без обязательного
внешнего IAM.

- [ ] **Архитектурное решение** (сначала!): встроенный OAuth2/OIDC-клиент в
      приложении vs брокеринг через IAM (Keycloak умеет всех перечисленных
      провайдеров из коробки — тогда в коде ничего менять не надо, только
      документация по настройке). Если встроенный — пункты ниже.
- [ ] Встроенный OIDC/OAuth2-флоу: `/auth/login/:provider`, callback, выпуск
      собственной сессии (cookie или свой JWT), refresh, logout.
- [ ] Провайдеры: Google, Yandex, VK (OAuth2 без полноценного OIDC — свой
      маппинг профиля), Apple (Sign in with Apple: свой JWT-клиентский секрет,
      ротация ключей). Конфигурация провайдера = client_id/secret + redirect.
- [ ] Таблица `users` (subject провайдера → локальный пользователь: имя,
      email, аватар) — связка с разделом 3 «Авторство».
- [ ] Привязка нескольких провайдеров к одному пользователю (по email или
      явная привязка в профиле).
- [ ] Роли: читатель / редактор / администратор — хранение в БД, назначение
      через админку (раздел 9); маппинг групп из JWT оставить для IAM-режима.
- [ ] **Группы пользователей**: локальные группы, назначение прав на группу,
      а не только на человека (используется в разделах 9–10).
- [ ] Экран входа: кнопки провайдеров (показывать только настроенных),
      режим `publicRead` сохраняется.

- [ ] **Модель данных**: таблица `projects` (ключ, название, иконка,
      описание, видимость), `pages.project_id NOT NULL`; миграция существующих

- [ ] **Ролевая модель на проект**: таблица участников
      (`project_members`: user × project × роль). Роли: читатель / редактор /
      администратор проекта. Глобальный админ (раздел 8) видит и управляет
      всеми проектами.
- [ ] **Видимость проекта**: публичный (читают все, в т.ч. анонимно при
      `publicRead`) / внутренний (все вошедшие) / приватный (только участники).
- [ ] **Гарды на бэке**: все проверки прав (`RequireEditor` и т.п.) становятся

- [ ] **UI**: переключатель/список проектов (сайдбар или главная), дерево и

- [ ] **Затронутые подсистемы** — пройтись по всем:
  - [ ] поиск: фильтр по проекту + права (раздел 1.1);

## 12. Кэширование (in-memory / Redis)

Кэш за единым интерфейсом; бэкенд выбирается конфигом. По умолчанию —
встроенный in-memory (ноль внешних зависимостей, в духе «одного бинаря»).

- [ ] **Интерфейс кэша** (`internal/cache`): Get/Set/Delete + инвалидация,
      TTL; реализация подключается по конфигу `cache.backend: memory | redis`.
- [ ] **In-memory (дефолт)**: LRU с лимитом по памяти/количеству + TTL.
- [ ] **Что кэшируем (первый этап — страницы)**: `GET /pages/:id` (контент),
      дерево страниц, брендинг. Позже — результаты поиска (короткий TTL).
- [ ] **Инвалидация** — самое важное: сброс при `PUT/PATCH/DELETE` страницы,
      move (дерево), импорте бэкапа/Confluence (полный сброс). Ключ версии
      страницы уже есть (`version`) — можно использовать для валидации.
- [ ] **Redis-бэкенд**, режимы подключения:
  - [ ] standalone;
  - [ ] **Redis Cluster**;
  - [ ] **Sentinel** (имя мастера + список сентинелов);
  - [ ] **TLS и без TLS** для всех трёх режимов (+ опц. mTLS: клиентский
        сертификат, свой CA, skip-verify для dev);
  - [ ] auth: пароль/ACL-пользователь.
- [ ] **Многоэкземплярный режим**: при in-memory и нескольких репликах
      приложения инвалидация не распространяется — задокументировать
      ограничение (in-memory = один экземпляр); для реплик — Redis
      (+ pub/sub-инвалидация, если понадобится гибрид).
- [ ] Конфиг в `appsettings.yaml`/env (`TEAMDOCS_CACHE__…`), позже — секция
      в админке (раздел 9) + кнопка «проверить подключение» и «сбросить кэш».
- [ ] Метрики: hit/miss в логи или `/api/health` (для начала достаточно).

## Порядок работ (рекомендация)

Этапы идут по зависимостям: сначала решения по инструментам и фундамент схемы,
потом защита данных, права и структура, затем удобства. Внутри этапа порядок
свободный.

Принцип: заранее делаем только **структурные** изменения схемы — те, что
трогают `pages` и требуют бэкфилла (project_id, авторство, deleted_at,
tsvector). Аддитивные сущности (комментарии, уведомления, page_views,
подписки) — новые таблицы, их проектируем в момент реализации фичи, не впрок.
